01 / THE PROBLEM

A model’s decision
isn’t authorization.

Agents read emails, browse pages, and respond to other agents. Those inputs can contain instructions you never intended to authorize.

SwarmAuth puts a verifiable permission check where a decision becomes an action: the tool itself.

01 The risky default

The agent asks. The tool trusts.

A compromised agent reaches a powerful tool with shared credentials. The model’s request becomes the permission.

02 With SwarmAuth

The agent asks. The tool verifies.

02 / THE MECHANISM

Explicit authority.
At every handoff.

A compact protocol between the issuer,
your runtime, and the receiving tool.

  1. 01ISSUER

    Define the grant.

    A trusted service decides which tool an agent may call, with specific capabilities and limits.

    policy → scoped permission
  2. 02RUNTIME

    Attach the token.

    Your runtime supplies a signed token when invoking the tool. Signing keys and grant policy stay outside the model.

    signed JCT · expires in seconds
  3. 03TOOL

    Verify, then execute.

    The receiving tool checks the permission and atomically reserves configured usage before running.

    allow within scope · reject otherwise

03 / THE CONTROLS

A permission has
more than an on switch.

Control what an agent can do, where it can do it, and how much authority it can use.

01

Scope the action.

Bind tokens to a recipient and capability. Pin sensitive arguments such as the order or destination account.

Capabilities
02

Keep delegation narrow.

Let a named worker narrow a grant once. Children share their parent’s limits and cannot expand its authority.

Delegation
03

Put a ceiling on the task.

Share call and currency budgets across fresh tokens and verifier processes with atomic Redis accounting.

Budgets
04

Make approval specific.

Authorize an exact resource revision and request. A single-use approval cannot be replayed with a fresh token.

Approvals

from swarmauth import guard, UsageTracker, use_token

# The issuer signs a policy-scoped token.
@guard(
    "tool:draft_proforma",
    issuer_public_key=trusted_public_key,
    tracker=UsageTracker(),
)
def draft_proforma(order_id: str):
    return {"order_id": order_id, "status": "draft"}

# Your runtime attaches the credential.
with use_token(scoped_token):
    draft_proforma(order_id="order-42")

THE IMPORTANT DISTINCTIONS

Clear boundaries.
Including ours.

Does SwarmAuth prevent prompt injection?+

It does not detect or eliminate prompt injection. It checks authority before execution, so a compromised model still needs a valid permission for the action it requests. A valid, overly broad grant remains dangerous; issuer policy and least privilege matter.

Is this a full OAuth implementation?+

No. SwarmAuth is a focused capability-token protocol and enforcement layer for agent-to-agent and agent-to-tool calls. It does not replace transport authentication, an identity provider, or all of OAuth.

Do I need a central authorization service?+

Signature verification runs locally against trusted public keys. A distributed deployment needs shared state when enforcing usage limits or revocation across processes. Issuance, key management, and deployment topology remain under your control.

What should stay outside the model?+

Signing keys, grant policy, trust registries, and the approval decision. Your trusted runtime supplies credentials, and tools enforce permissions. Business validation, safe side effects, and idempotency still belong in your application.
